# Muxpilot acceptance and release evidence

Status: implementation contract for planning review; no implementation, provider support, or production readiness is implied. Baseline: Muxdeck `96769f6`, Multica `e31da86`. Requirement references F01–F12 and N01–N04 follow the product specification. Scenario IDs below are stable references for implementation tasks and release reports.

## Scope and test discipline

The acceptance target is a configured supported interactive main agent session that can receive “Use Muxpilot for ~/git_farm/shop. Add password reset end to end, and open a PR when tested.” One-time installation loads the Muxpilot tools/instructions through the provider's supported mechanism; activation resolves project context and coordinates Multica work while people observe and steer in Muxdeck. An unconfigured session reports the missing setup without pretending tools were injected. No per-project CLI, configuration file, or mandatory structured brief is part of the happy path.

Multica owns current project/epic/task/run state. The project journal owns the durable local history, recovery intentions, and evidence references; it does not silently replace Multica authority. The main coordinator and daemon-owned bridge workers have separate lifetimes. v1 supports an interactive main session and structured worker output mirrored into tmux. Worker native TUI takeover is deferred; keyboard input into a bridge pane must never be forwarded as if it were a supported worker interaction.

Use deterministic fake providers, a fake Multica event source, temporary repositories, isolated tmux sockets, and disposable project state by default. Inject faults at explicit checkpoints rather than relying on timing races. One representative browser scenario covers each distinct wiring or interaction risk; exhaustive event permutations, path resolution, authorization, state transitions, and idempotency belong in inexpensive unit or contract tests. Do not add a second test layer solely to repeat the same assertion.

Real-provider smoke runs require explicit authorization for their account/cost and use an isolated temporary repository and tmux socket. Existing valuable sessions are never test fixtures. Authorization to use GPT-6.1-sol development subagents does not itself authorize authenticated Muxpilot provider smoke runs. A passing fake-provider suite does not certify a real provider pairing. A real smoke proves only the exercised capability and provider/version/account combination.

## Gates and definitions of done

### Planning gate — before implementation

- Product behavior, architecture, cross-repository API contracts, technical decisions, task ownership/dependencies, and this acceptance matrix agree on identifiers, state authority, lifecycle, and authorization.
- Every F/N requirement has at least one scenario or an explicit review/evidence check; every planned implementation task names its acceptance IDs and completion evidence.
- The bounded gate for selecting and proving an exact main-agent/worker-provider pairing is assigned to MXP-003, with a capability probe plan and a clear unsupported-capability response; planning publication does not claim an installed/versioned pairing has been selected or tested. Neither repository is assumed to supply missing APIs without a task to implement them.
- The durable Multica event feed, human-only live-steering API extension, daemon-owned worker lifecycle, fencing, and project authorization have concrete implementation owners and failure behavior.
- Scope explicitly distinguishes first demo, complete v1, and deferred native worker TUI takeover. Open decisions that affect correctness block their dependent tasks rather than becoming optimistic defaults.
- Review confirms no code, dependency installation, live session operation, or feature deployment happened merely to produce these documents.

### First demo gate — deliberately narrower than v1

A disposable repository completes one bounded end-to-end goal using the selected pairing: normal main session activation; project/epic creation; at least three substantial worker runs in visible grouped sessions; a human steering event; integration; a representative test; and a verified deliverable. Show links from tasks to their exact runs and from completion to evidence. MXP-018 durable feed is implemented before MXP-019 terminal links; demonstrate one attributed human edit/steering trace, while exhaustive feed retention, audit and recovery coverage remains a full-v1 gate. Demonstrate a main-session crash with workers continuing under the healthy daemon and coordinator reattachment without duplicate work. A fake-provider demo is labeled as such; calling the pairing validated requires A02 real capability evidence. No real external PR is created without the authorized isolated smoke scope.

The demo report lists omitted v1 scenarios. A demo pass does not authorize release or imply daemon-crash recovery, comprehensive authorization, or all journal durability checks have passed.

### Complete v1 gate

All applicable A01–A26 scenarios, A27 premerge rehearsal evidence, and the full fault matrix pass on the intended release commits in both repositories before default-branch merge. A27 live post-deployment evidence closes delivery afterward; it is not a prerequisite that would deploy the feature before its source gate. Missing evidence, unsupported required pairing capabilities, unverified outcomes, and unresolved safety/recovery failures block release. Required CI checks pass; targeted local checks and browser coverage demonstrate changed behavior; the deployment/runbook review and backup/restore exercise pass. Release evidence identifies the exact Muxdeck and Multica commits and supported pairing. Merge to actual Muxdeck `master` and the authorized writable Multica fork/default `main` follows the agreed integration order; upstream Multica merge authority is not assumed; feature branches are not deployed early.

## Fault-injection matrix

Run each boundary against at least worker creation and one mutating control/integration operation. Use operation IDs and fault checkpoints to prove the state, avoiding sleeps. The journal commits intent before dispatching an external effect; a receipt is recorded after a confirmed result. Recovery classifies the outcome before deciding whether replay is safe.

| Injected boundary | Recovery assertion | Evidence |
| --- | --- | --- |
| Before intent transaction commits | No effect was dispatched; no phantom committed intent | Journal transaction and external call count |
| After intent commit, before send | Pending intent is reconciled; permitted replay uses same operation identity | Committed intent, zero initial calls, replay ledger |
| After send, before external acceptance | Resolve status with authoritative external lookup; retry only if absent or idempotent | Lookup and external operation count |
| External acceptance, before receipt is returned | Recover accepted run/effect by stable identity; never spawn a duplicate | External run ID, linked intent, reconciled receipt |
| Receipt received, before local receipt commit | Same reconciliation as lost receipt; memory is not recovery evidence | Persisted recovery event and external status |
| After receipt commit, before task/UI projection update | Replay durable events repairs projection without repeating effect | Rebuilt projection and exactly-once effect count |
| Artifact written, before reference committed; reverse order failure | Orphan is recoverable/cleanable by policy; absent reference target is explicit; no false success | Artifact manifest and missing/orphan diagnostics |
| Main crash with healthy daemon | Worker lifetime unaffected; new main fenced until lease acquired | Independent PIDs and worker progress after crash |
| Daemon crash with healthy main | Detect unavailable owner; reconcile actual worker fate separately | Process/run inventory before and after restart |
| Lease expires or revoked while request in flight | Receiver rejects stale fence or outcome remains reconcilable; successor does not blindly duplicate | Both controller epochs, enforcement and reconciliation records |
| UI edit, cursor loss or reconnect during effect | Durable feed retains human change; reconciliation applies current authority and records conflict | Original event IDs/cursors, decision history |
| Host/process restart with committed WAL pages | Committed intent/events remain; external state is queried before effects | Isolated restart/restore integrity report |

`WAL` plus `synchronous=FULL` is a durability configuration, not proof against every storage/controller failure. Process-crash tests and consistent backup/restore are required; host/power-loss claims require an appropriate storage fault harness and otherwise remain explicitly unclaimed.

## Event-to-artifact contract

A release fixture must let a reviewer follow one goal through activation and project resolution, authorization/capability checks, plan version, task/run creation, worker dispatch, progress/output, human edit/steering, retry/stop, integration, verification, closure, and recovery. Record stable project/epic/task/run/session identities and distinct provider execution UUIDs, event and operation IDs, actor/source, controller epoch, provider identity, cursor where applicable, input version, timestamps, outcome/uncertainty, and evidence references as appropriate to the event. Sensitive raw values are excluded.

For each event class, assert required fields, ordering/causal references, replay behavior, and artifact existence/hash when referenced. Exports preserve source IDs and uncertainty; they must not flatten multiple attempts into a fictional success. Human UI/worker events need a durable feed contract with retained cursors, catch-up and explicit retention-gap behavior. A current-state polling snapshot cannot prove who changed a task or recover an intermediate stop/retry and therefore fails this contract.

## Test tiers and release evidence

| Tier | Purpose | Execution expectation |
| --- | --- | --- |
| Unit | State transitions, auth matrix, path/identity mapping, journal transactions, event dedupe, fencing and exports | Fast deterministic cases; exhaustive inexpensive combinations |
| Contract/integration | Multica API/feed, daemon ownership, provider adapter capabilities, journal/repository/tmux effects | Isolated services/repos/sockets; fault checkpoints; meaningful independent outcome checks |
| Component/browser | Grouping, exact run navigation, human steering, stale link, closed pane history and unsupported bridge input | Representative scenarios for distinct user-visible risks; affected specs only locally |
| Authorized provider smoke | Confirm chosen pairing really supports promised actions/lifetime/structured output | Explicit account/cost authorization; disposable repo/socket; record exact supported scope |
| Release/operations | CI, migration/backup restore, staging install, scoped health/recovery and rollback | Both repository commits; existing runbook and shared deployment tooling |

Local validation begins with affected frontend tests (`npm run test:related -- <changed source>` or `npm run test:changed`), explicit affected backend/daemon test files, contract tests for API changes, and affected browser specs. Full suites remain in CI and run locally where broad impact or unresolved uncertainty warrants them. Once appropriate checks pass, do not repeat or broaden them without a new change, failure or unresolved concern.

The release bundle contains:

- A scenario ledger with pass/fail/not-applicable and rationale, test IDs, commit IDs, pairing versions, fixture/provider mode, and links to raw evidence; no unsupported “all passed” summary.
- The event-to-artifact manifest, fault-matrix results, journal/schema integrity checks, backup/restore report, authorization/secret scan, and known limitations/deferred capabilities.
- Integration review for both repositories, required CI run/job IDs and GitHub timestamps, branch/merge targets, relevant contracts/version compatibility, and the final verification/PR evidence for the demo goal.
- The current `AGENT_DEPLOYMENT_GUIDE.md` reviewed completely before operational actions; deployment plan with scoped identities, backups, migration/compatibility checks and rollback behavior. Build frontend artifacts in staging, never live `dist/` before validation. Reuse `scripts/check_deployment.py` and retain its report; documentation-only planning requires no build or service restart.
- A private task timeline via `scripts/task_timeline.py` that wraps commands, tests, staging, push, CI waits and deployment; records phase changes and GitHub timestamps; and includes its generated report. Report command runtime separately from total task elapsed time and intervals between commands.

Release may not expose the unauthenticated console publicly, restart tmux, kill an unscoped server, or destroy live sessions without explicit human direction. Test and release evidence must demonstrate preservation of unrelated work. Routine push/deploy authorization does not widen those safety boundaries.
